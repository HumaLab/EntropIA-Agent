# Research archive failures

Research Agent runs over one or several corpora often end with archive batches without claims and an unclear error.
Goal: the run should not fail; when it does, show a clear message and a retry button, like batch processing.

## Specs

- S1. A research run over one or several corpora must not lose archive batches: "lo ideal es que no falle".
- S2. When a run fails, the user sees a clear message: "si falla tenga un mensaje claro".
- S3. A failed run or batch offers a retry button: "y un botón de reintento, como se hace en los procesameintos por lotes".
- S4. The error currently shown and judged unclear, verbatim: "Limitaciones\nsalida de archivo no parseable; lote registrado sin claims\nDegradación del pipeline: Salida inválida de asistente_archivo: la salida no contiene JSON recuperable (asistente_archivo, 4 veces)."

- S5. Decision (L13): when an archive batch still fails after being split, the run pauses with a clear message naming the batch, and Resume retries that same batch. No evidence is skipped. Option chosen verbatim: "Pausar y ofrecer Reanudar (recomendado)".
- S6. Scope (L13): engine only for now; option chosen verbatim: "Motor ahora (T2, T3, T5)". T4 (desktop) waits.

## Tasks

- T1 [S1-S4] Monitor the live run and record each failure in the Log. Route: parent inline, read-only. Commit: none.
- T2a [S1, S2] Client: read `finish_reason`, raise the output cap from 4096 to 16384 tokens. Route: inline, test-first (tests/cliente_llm.rs). Commit: pending.
- T2b [S1, S2] Engine: classify a truncated or empty answer with a clear error and skip the pointless repair; on archive failure, retry the same offset with half the input (48 KB, 24 KB, 12 KB). Route: inline, test-first (tests/investigacion.rs). Commit: pending.
- T3 [S1, S3, S5] Engine: a batch that still fails after the split writes no checkpoint and pauses the run with a clear `research_error`; Resume retries it. Route: inline, test-first. Commit: pending.
- T4 [S2, S3] Desktop (EntropIA-Pro-Lite, outside this repo): clear error and a retry button modeled on `retry_batch`. Route: deferred by S6. Commit: none.
- T5 [S2] Client: OpenRouter 403 key limit becomes a clear message without the raw JSON or key URL. Route: inline, test-first, same unit as T2a. Commit: pending.

- L5 (evidence): a failed batch still advances `next_offset` (`src/investigacion.rs` around 2070-2083), so its evidence is skipped for good; the engine has no batch retry. Desktop reference for retry: `EntropIA-Pro-Lite/.../processing/commands.rs` `retry_batch`.

- L8 (monitor): batch 2 failed the same way: empty raw, 0 claims, repair failed (`llm_calls.error` = "la reparación de asistente_archivo tampoco cumplió el contrato"). Earlier roles on the same model (prospeccion, investigador_principal) returned usable text, so the empty output is specific to the archive role (~47 KB input).
- L9 (monitor): batches 3 and 4 failed the same way (empty raw, 0 claims). Batches 1-4 had ~47 KB inputs. Batch 5 (10 KB input, 7 fragments) answered with 4130 chars of text that still end mid-`limitations`, so it was cut too; the repair rescued it (8 claims). Cost per call is almost constant: ~US$0.0043 for 47 KB inputs, ~US$0.0025 for the 10 KB one. The difference tracks only the input size, which points to every archive call using up the same fixed 4096-token output budget. Working hypothesis, consistent with L3: the model's reasoning tokens count against `max_tokens` 4096. With a large input they use up the whole budget and `content` comes back empty; with a small one only a cut tail is left. Unified root cause for both jobs: the 4096 output cap, with no `finish_reason`/`usage` check.
- L10 (monitor): 17:30:10, OpenRouter `403 Forbidden` "Key limit exceeded (monthly limit) ... $5.00 of $5.00 used; resets 2026-12-01". This is handled correctly as fatal: job paused, batch 5 not lost, and resume at 17:37 continued from it. But the user sees the raw provider JSON, which includes the key-management URL. It should be translated into a clear message: monthly key limit reached, how to raise it, then resume.
- L11 (monitor): result of this run: 4 of 5 archive batches (170 of 177 documents) had no claims; only batch 5 contributed claims (8). Archive cost US$0.035 over 11 calls, most of it spent on empty answers.

The report lists 4 times "salida de archivo no parseable; lote registrado sin claims" and only "(asistente_archivo, 2 veces)" under "Degradación del pipeline". The job also closes as `completed` with 96% of the evidence unread, and nothing in the final state tells the user that a retry would help.
